# Formal and Rust coverage

This matrix separates properties proved about the Lean model from behavior
compared against production Rust entry points. `PROVED MODEL` means Lean's
kernel checks a theorem about that model. `TESTED RUST` means the differential
bridge compared generated inputs with the named production entry point. A bridge
pass covers its generated domains and assumptions. It does not prove that the
model covers every Rust behavior or that Rust refines the model.
`TESTED BOUNDARY` means the bridge's request and response checks passed.

The latest recorded bridge run generated 1,000 requests for each of its six
families. Its comparisons, negative controls, and protocol boundary checks
completed, and it also included retained regression cases. The bridge treats
`unsupported_domain` and `fuel_exhausted` as valid comparable outcomes. The
request count therefore does not show that all 6,000 requests exercised a
supported Rust operation. Run the gate with
`cargo run --example semantic_bridge -p ish -- --family all --cases 1000`.
The family adapters and their selected domains are listed below.

The Lean model uses finite fuel. Exhaustion is an explicit outcome, not a proof
of termination. Evaluation and effects models receive command and filesystem
observations; they do not prove the observed external behavior. The models do
not prove parser correctness outside their generated inputs, kernel descriptor
safety, terminal behavior, process scheduling, or Rust implementation
equivalence.

The audit discovers theorem declarations from each expected family namespace.
It rejects a missing family, a family with no theorem, an axiom declaration in
a family, and transitive axioms outside `propext`, `Quot.sound`, or
`Classical.choice`. It also rejects theorem links above that do not name an
audited declaration. Run it with `cd formal && lake env lean IshSemantics/Audit.lean`.
This invocation rereads this coverage document. A
cached Lake module build can replay an earlier audit result.

The Lean octet round-trip law proves the model's byte map. It does not prove
every Rust string conversion or OS boundary. Production `ShellBytes` stores raw
bytes. The PUA encoding in `encoding.rs` carries arbitrary bytes through Rust
text paths and escapes literal marker characters so decoding is reversible.
It is an implementation codec, not the Lean model's octet representation.

The bridge checks Rust behavior on generated, validated inputs. It does not
prove implementation refinement. Aeneas and Charon were unavailable, so no
translation or refinement proof connects Rust code to Lean. The Lean theorems
remain claims about the Lean model; Rust tests and the bridge provide the
implementation correspondence evidence described above.
